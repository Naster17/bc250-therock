## Everyday commands

```bash
# Standard Torch scripts and GPU identity
bc250-torch your_script.py
bc250-torch ~/bc250work/torch-matrix.py
bc250-torch -c 'import torch; print(torch.cuda.get_device_properties(0).gcnArchName)'

# Torch with the frozen Transformers/PEFT/Accelerate environment
bc250-train train.py
bc250-train -c 'import torch, transformers, peft; print(torch.__version__, transformers.__version__, peft.__version__)'

# External datasets and writable checkpoints
bc250-train --mount-ro /mnt/datasets --mount /mnt/checkpoints train.py

# Interactive shell in the selected environment
bc250-torch --shell
bc250-train --shell
```

Explicit mount sources must exist. Both launchers preserve the host home,
working directory and script paths. Checkpoints/downloads under those mounts
persist and belong to `nik`. Containers run as UID/GID 1000 after normal `doas`
authentication. Tokens can be exported or supplied through a private env file.

`bc250-train` selects the frozen consumer packages of the current runtime.
Changing Python package versions or replacing its `PYTHONPATH` changes that
qualified environment. Extra dependencies can be installed into a host directory
using `pip --target ... --no-deps`; see [bc250_torch_usage.md](bc250_torch_usage.md)
for data paths, shared memory, environment and package examples.

## Known limitations for this snapshot

- SDMA is deliberately disabled; the experimental gfx1013 VM heap is disabled by default.
- Scalar backends are used where hardware matrix instructions are unavailable.
- hipBLASLt device GEMM, hipTensor contractions and hipSPARSELt device support remain incomplete.
- FlashAttention, memory-efficient attention, QLoRA/4-bit backends and distributed training are not qualified.
- Larger models/sequences, multi-hour training, near-capacity/OOM behavior and deliberate GPU fault/reset recovery remain future qualifications.
- Hardware clock telemetry is unreliable under load; hardware counters and advanced profiling remain separate work.

GPU GTT and CPU RAM share the board's physical memory. Budget model weights,
activations, gradients, optimizer state and DataLoader memory together. The 1 GiB
`/dev/shm` default limits worker IPC, not total GPU or container RAM.

This release supports ordinary use within the documented scope. A failure on a
new workload should retain its traceback, command, package versions and kernel
messages for the next development session.

## Rollback and preservation

The prior independent ROCm/Torch release remains selected by
`/opt/bc250-stack/previous`. Its original scope is smaller: the new frozen
training package directory belongs to the current reviewed release. An older
runtime without that directory will cause `bc250-train` to stop with a clear
message; standard `bc250-torch` remains the baseline rollback entry point.

To select the fallback atomically, retain the current target and use root:

```bash
doas sh -c '
  readlink -f /opt/bc250-stack/current
  ln -s "$(readlink -f /opt/bc250-stack/previous)" /opt/bc250-stack/.rollback-current
  mv -Tf /opt/bc250-stack/.rollback-current /opt/bc250-stack/current
'
```

The printed original target restores this reviewed snapshot with the same
atomic-link procedure. Do not switch releases while a workload is running.
Rollback changes a pointer; it does not delete either release or any checkpoint.
The review's `release.json` records both targets.

**Preserve everything for development resumption:** local/nested Git repositories,
all source snapshots, build directories, ccache, ROCm/Torch/Triton work trees,
images/containers, tests/logs, consumer environments, models/checkpoints and both
versioned runtimes. No expunge, prune, cache wipe or old-runtime cleanup was done.

The GRUB boot files under `/home/nik/bc250work/bc250-rocm-lab` must remain.
The working kernel and existing watchdog keepalives remain configured. Watchdog
reset behavior under a GPU fault has not been proven; normal CPU keepalives can
continue during a GPU hang.
