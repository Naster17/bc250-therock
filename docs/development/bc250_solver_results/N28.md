# N2.8 bounded device Schur control — 2026-10-18

Completed the recorded N2.8 scope: the isolated small complex Schur candidate
now offers explicit `schur(a, qr_backend="device_control")`. A single HIP launch
consumes trailing deflations, selects the shift, executes at most one cooperative
QR/similarity step and checks finite/Hessenberg-fill status. One five-int status
record returns to the host per launch. The default helper remains `reference`;
production Torch nonsymmetric eig remains host LAPACK.

## Implementation and fixed contracts

Extracted the N2.7 QR arithmetic into a shared device function, used by both
kernels. N2.8 adds a 32-thread control kernel around it, using an owned shared
matrix so input tensors remain unchanged. State is active order, QR iterations,
deflations, iterations since deflation, and phase. Phase distinguishes continue,
converged, budget exhaustion and nonfinite/excess fill. Trailing deflations are
checked before the budget, preserving triangular/zero-budget success semantics.
The host enforces at most budget+1 launches, reads terminal status, and retains
finite checked rescaling to original units. Positive info remains unconverged;
there is no hidden host matrix solve or successful fallback.

The unchanged rules include component normalization; order<=16; integer budget
0..4096; eps*(|diagonal pair|)+tiny deflation; nearest trailing2x2 complex shift;
exceptional shift every20 iterations without deflation; finite/128eps Hessenberg
fill check before removing roundoff fill; separated-spectrum right recovery,
8sqrt(eps) gap floor and its original residual bounds. Principal complex square
root is implemented explicitly, with real-negative/zero branch controls.

The C ABI and step wrapper are private, expecting matching contiguous normalized
complex tensors, distinct owned outputs and valid driver state. This is not a
new public rocSOLVER API. Existing public helper guards still reject unsupported
inputs, larger shapes and requires-grad. No batching, balancing, autograd,
compile/graph/concurrency or general convergence claim is added.

Separate TorchDispatchMode instrumentation shows intercepted scalar reads at
orders4/9/16 changing from43/88/159 to8 for complex64 and47/116/207 to8 for
complex128. Those eight remaining scalar reads do not mean eight total host
synchronizations: N2.8 explicitly performs9/19/35 and10/26/47 D2H status copies,
respectively, one for every QR iteration plus the terminal launch. ATen call
counts also fall (order16:2686→412 and3430→448). These are Torch-level counts,
not all C++/HIP activity; profiler traces provide separate GPU evidence.

Production host eig controls stay~0.230–0.421ms before/after blocks. Even the new
Schur-only stage is much slower than that full eig path. These six warm-cache
fixtures on one board and three samples/pass establish only the bounded
prototype gain, not general/sustained/model/LoRA performance or production GPU
eig readiness. Preparation and remaining per-iteration transfers still matter.
